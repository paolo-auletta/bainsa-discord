BAINSA bot message system

Visual prototype · illustrative content

One language. Four message purposes.

Every bot response chooses its renderer from the job it performs. Semantic tone communicates state; the renderer communicates how the message should be read and how long it should live.

1. PurposeEvent, document, interaction, or handoff.
2. StateInfo, success, pending, changed, danger, or neutral.
3. ContentSubject, scope, facts, actions, privacy, and provenance.
4. RendererOne shared payload contract produces the Discord message.
Design decision

Colored cards remain for chronological events. Plain documents carry maintained truth. Panels own interaction. Direct messages stay linear and action-oriented.

Event card

A scannable append-only record of something that happened. Color and the state mark reinforce meaning; the words remain sufficient on their own.

Order: event → subject → scope → change or result → resulting state → actor.

Complete product coverage

The component language is now tested against the entire implemented Discord surface: every slash command, every durable document, each creation flow, and each distinct user-facing outcome contract.

Coverage is counted by distinct user-visible state, not by every backend exception string that shares the same recovery treatment.

17Slash commands, including the role-aware guide
3Complete creation and editing flows
15Shared terminal and recovery contracts
4Purpose-built message primitives

The three flow sections include all screens, alternate branches, terminal states, ownership/expiry protections, and downstream messages. The command atlas covers every successful mutation, lookup, no-op, private-only change, reconciliation state, notification handoff, and failure family.

Every bot command

A command-by-command contract for what the actor sees, what the board sees, what the affected member receives, and how failures recover.

Open a group to inspect its complete output map. Private reasons and notes never cross into board-visible activity.

Onboarding and access lifecycle

The complete applicant, reviewer, resolution, and arrival experience for both Researcher and Alumni paths.

Applicant controls remain private. Review history stays in the university board space. The decision and useful next step reach the applicant directly.

People profile lifecycle

Creation, editing, publication, directory synchronization, retry, cancellation, and unpublishing in one actor-bound Components V2 flow.

Draft content stays private and in memory. Only confirmed publication crosses the database boundary and creates or updates the canonical forum post.

Project creation lifecycle

The complete five-step setup, validation model, durable commit boundary, Discord reconciliation, board activity, canonical documents, and team handoff.

Before commit, retry preserves the draft. After commit, no setup retry is offered: Discord work reconciles automatically to prevent duplicate projects.

Shared outcome library

Every command and flow resolves through one of these reusable terminal or recovery contracts. Domain-specific copy changes; message anatomy does not.

Each outcome names committed state, Discord state, privacy, and the next safe action. Color supports the words rather than replacing them.

Shared architecture

Domain formatters describe meaning. The design-system layer owns presentation, Discord limits, safe mentions, and consistent empty states.

No service should construct raw embed fields, Markdown spacing, or semantic colors independently.
