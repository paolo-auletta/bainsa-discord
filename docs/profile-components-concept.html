Public-card hierarchy

1. Person

Full name makes the post legible when opened from search, tags, notifications, or a copied forum link. The headline gives a human shorthand, not the only identity.

  • full_name — canonical
  • headline — member-authored

2. BAINSA identity

A fixed, scannable strip sits before biography. It states the member path, university, and division only when the canonical membership supplies one.

  • member_type — canonical
  • university_name — canonical
  • division_name — canonical, optional

3. Collaboration signal

Current focus, then what the person wants to explore. These explain why a reader might contact them, without competing with identity.

  • current_role, organisation, location
  • goals, about

4. Discovery and contact

Managed tags remain forum-native filters. Contact is a deliberately chosen action; Discord is the default route and no unused field gets a “Not added” placeholder.

  • Canonical university tag + selected tags
  • Only opted-in public contact details

The alumni case

An absent division is not an empty field. The identity strip simply contains two facts.

Every profile component, by responsibility

Directory guide

Public guidance speaks to the whole community: “Browse member profiles by interests, current work, and BAINSA context.” Owner actions stay as clearly labelled buttons.

  • Create or update my profile
  • Unpublish my profile

Current / direction / tag / contact screens

Private, progressive screens use “you” because they are only visible to the owner. Each has one purpose, a review summary, back navigation, and Cancel.

  • Required fields block only forward progress
  • Optional contact is visibly optional

Review screen

Names the visibility boundary in plain language. It previews public content, not hidden operational IDs, persistence state, or private reconciliation detail.

  • Explicit publishing notice
  • Publish, Back, Cancel

Terminal states

Publishing, pending sync, failure, unpublish confirmation, and cancellation are concise private messages. They explain the outcome and recovery path; never echo sensitive profile data.

  • Saved; syncing automatically
  • Unpublished; cleanup retries if needed

Recommended implementation slice

  • Use formatProfileReview for the owner-only wizard and a separate public post formatter for the reader-facing card. Owner-centric “your profile” language stays private.
  • In the public formatter, lead with the canonical full name and an identity line: Researcher · Bocconi · Analysis. Build that line only from reconciliation-loaded membership facts.
  • Keep division conditional: researchers with a current division display it; alumni do not receive a blank or placeholder division row.
  • Render authored sections after canonical context, and omit optional fields that are absent. Keep Markdown escaping and allowedMentions: { parse: [] } unchanged.
  • Update the people-directory guide to address readers (“Browse profiles…”) and label the owner buttons separately (“Create or update my profile”).
  • Use the existing thread/message identity and reconciliation generation unchanged, so a profile update edits one tracked starter card rather than creating a duplicate post.

Acceptance-test map

Hierarchy

Assert public content includes the member name and canonical member path, university, and division; confirm ordering places identity ahead of biography.

Copy boundary

Assert public content does not contain “Your BAINSA … profile”; keep “your” language in private review and modal components.

Privacy

Assert absent optional values and unpublished/draft content are omitted. Continue testing escaping and inert mentions for authored content.

Reconciliation

Retain the existing upsert identity test and add a content-change case proving the same forum thread/starter message is edited in place.
